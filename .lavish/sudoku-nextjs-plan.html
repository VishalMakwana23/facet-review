Product plan · puzzle game

Build a focused Sudoku experience in Next.js.

A local-first Sudoku app with reliable puzzle generation, an accessible 9×9 grid, notes, validation, pause/resume, and refresh-safe progress—small enough to ship and structured enough to grow.

Plan boundary

Plan only—no implementation yet. Optimize for puzzle correctness, fast mobile input, keyboard and screen-reader access, and a clean path to future daily challenges.

Goal, current state, desired behavior

Treat Sudoku as a new Next.js app surface. The domain layer must be independent from React so puzzle correctness and persistence can be verified without a browser.

Goal

Ship a browser-playable Sudoku loop that starts quickly, feels calm and predictable, and makes every board state understandable.

Desired behavior

User selects a cell, enters a digit or note, sees conflicts immediately, pauses when needed, refreshes safely, and receives a clear completion summary when the puzzle is solved.

Proposed architecture

Use Next.js App Router for the page shell and a narrow client boundary for interaction. Keep puzzle rules, generation, solving, and persistence behind explicit TypeScript contracts.

Risks and mitigations

Puzzle generation is slow

  • Use seeded generation, bounded attempts, a deterministic solver, difficulty scoring, and known-good fallbacks.

Grid is inaccessible

  • Use roving tabindex, explicit cell labels, live announcements, visible focus, and non-color-only cues.

Saved state is corrupt

  • Version snapshots, validate on read, migrate known versions, and expose a reset-game action.

Mobile entry is frustrating

  • Use generous touch targets, sticky keypad behavior where useful, selected-cell emphasis, and real-device checks.

Acceptance checklist

Every puzzle has exactly one solution and matches its difficulty band.
Given cells cannot be edited; values and notes are safe to change.
Conflicts are visible and announced without relying on color alone.
Keyboard users can navigate, enter, erase, toggle notes, pause, and restart.
Touch users have large controls for digits, erase, notes, pause, and new game.
Refresh restores puzzle, values, notes, timer, and preferences or starts clean.
The layout works at 320, 375, 768, and 1440px without horizontal scroll.
Vitest, component tests, Playwright, and production build all pass.

Recommended first slice

One seeded Sudoku board, three difficulties, full local play.

Prove the domain and interaction loop before investing in daily challenges, hints, accounts, or social features. The most valuable early feedback is whether the board feels clear and forgiving on both keyboard and touch.

Explicitly out of scope
Accounts · cloud sync · leaderboards · online play · AI hints · ads · complex state management

Open questions before implementation

  • Should mistakes be highlighted immediately, or only when the user asks to check?
  • Should notes be entered with a persistent toggle or a press-and-hold shortcut on touch?
  • Should “hard” be defined by clue count, solver technique score, or both?
